# Design: Telegram Connector

## Context

웨지 A 1차 채널. 에이전트 코어(`lib/tools`)와 웹 채팅은 동작 중. 글로벌 유저 도달과 그룹 바이럴이 목적이라 로컬에서도 돌아가는 롱폴링으로 시작(웹훅·SSL·공개 URL 불필요).

## Goals / Non-Goals

**Goals**
- 기존 에이전트 코어 무수정 재사용 (툴·장부 그대로)
- 개인/그룹 채팅 동작, 채팅방별 멀티턴 메모리
- 로컬 기동: `npm run bot`

**Non-Goals**
- 웹훅 배포/서버리스, 다중 인스턴스
- 그룹별 영속 메모리(DB) — 인메모리, 재시작 시 리셋 (MVP 허용)
- 텔레그램 인라인 버튼/결제 등 부가 기능
- 실거래 (Phase 2 별도 변경)

## Decisions

1. **전송 방식: getUpdates 롱폴링 (raw fetch)**
   - 이유: 공개 URL 불필요, 프레임워크(grammy/telegraf) 없이 의존성 0. 대안인 grammy는 편의 대신 의존성·추상화 추가 — MVP 볼륨에서는 raw가 오히려 단순.
2. **응답 생성: `generateText` (비스트리밍)**
   - 이유: 텔레그램은 완성된 메시지를 보내는 게 자연스러움. 스트리밍은 메시지 편집 남발이 됨.
3. **메모리: 인메모리 Map<chatId, ModelMessage[]>, 상한 16개**
   - 이유: MVP 단일 프로세스 전제. 유저/어시스턴트 텍스트 턴만 저장(툴 호출 결과는 장부가 source of truth).
4. **코어 공용화: `lib/llm.ts`(모델 생성), `lib/prompt.ts`(시스템 프롬프트) 추출**
   - 이유: 웹 라우트와 봇의 브레인 불일치 방지. 수정은 import 교체뿐.
5. **환경변수 로딩: dotenv**
   - 이유: `tsx`는 Next의 `.env.local` 자동로딩이 없음.

## Risks / Trade-offs

- [롱폴링 중복 실행 시 텔레그램 409 에러] → 409 감지 시 "봇 인스턴스 중복" 안내 출력
- [인메모리 메모리 → 재시작 시 맥락 소실] → MVP 허용, 스펙에 명시
- [그룹 프라이버시 모드 기본값으로 멘션만 수신] → 멘션 필터 요구사항과 일치, 추가 설정 불필요
